# 2026-11-05 — GPU、策略组合与 Parquet 存储选择

## 一、目前怎样选择计算资源

当前项目以 CPU 为主最合适。行情解压、事件调度、盘口更新、订单状态和收益核对都沿着时间顺序推进。现有 C++ 回放入口对一个交易日使用单线程，增加 CPU 核数可用于同时运行多个日期和参数组合。

线性模型和 LightGBM（梯度提升树模型）先在 CPU 上建立可重复的基线。研究流程先确定特征、标签、时间顺序验证和交易成本，再比较更复杂模型。服务器优先满足 CPU、内存和 SSD 容量，推荐配置见单独文档。 [服务器配置与费用](server_recommendation.md)

| 工作 | 当前优先资源 | 何时值得评估 GPU |
| --- | --- | --- |
| 行情转换和 C++ 回放 | CPU、内存、SSD | 先测量解析和事件处理的瓶颈 |
| 探索性特征与最终实时特征 | 离线Polars CPU，最终入选特征由C++计算 | 出现适合大批矩阵运算的步骤时单独比较 |
| 线性模型 | CPU | 在实际大矩阵和重复拟合上测量总成本 |
| LightGBM | CPU，按日分区和滚动训练 | 较大训练集或多次调参使训练成为主要耗时，再比较 GPU 后端 |
| 神经网络、序列模型 | 根据模型规模评估 GPU | 确定需要该类模型后，用小规模实验测算显存、训练时间和效果 |
| 多策略与执行参数组合 | 多核 CPU、预测缓存、分批回放 | 若某一评分或模型步骤支持批量 GPU 计算，独立测其收益 |

GPU 版本的训练可能改变数据搬运、预处理、精度和依赖要求。比较时固定数据、模型目标、验证划分及参数范围，记录“读取 + 预处理 + 训练 + 预测”的总时间和费用。LightGBM 的 GPU 后端也要核对编译方式及平台支持，避免只比较训练核心的一小段时间。

当前给出的是资源选择依据。未来模型的 GPU 加速比要由实际模型和数据测得。

## 二、策略组合怎样控制运行量

仅依赖行情的特征可以按日期和定义版本预先计算。固定模型的预测也可以缓存，多个入场阈值、退出规则、持仓限制和执行参数组合复用这些预测。

库存、在途订单、排队状态和成交结果随每次交易回放变化。每组执行参数应独立运行原生引擎，保留自己的订单和账本，随后再汇总组合收益与风险。

先以少量、具有明确对照关系的组合筛选，在验证区间确定参数后再进入最终测试。并发按日期或参数组分配进程，给训练和转换设置各自的内存预算。实验清单记录数据版本、特征版本、模型、参数、代码版本和实际运行日期。

## 三、是否可以统一使用 Parquet

原始行情归档、特征、标签、预测和研究结果，都可以按清晰的字段结构使用 Parquet。Parquet 将相同字段集中存储，支持只读所需列和按日期筛选，适合多日研究。压缩算法先选 ZSTD 级别 3，在容量与读写耗时之间取得实用平衡。

现有 C++ 引擎的文件入口使用 NPZ 中的 `data.npy`。当前可行的分层方式如下。

```text
官方成交ZIP + 网盘25档快照CSV.zst
                ↓ Data标准化
standard/版本/{snapshots,trades}/日期.parquet
                ↓ Polars特征组与标签
features/版本/日期.parquet
labels/版本/horizon=周期/日期.parquet

L2增量 + 对应逐笔 → NPZ事件缓存 → C++原生回放
```

当前标准行情与分组研究Parquet入口已经实现。base列与衍生列共同保存在每日特征文件，标签按版本和预测周期独立保存。NPZ用于C++事件回放。

若希望 C++ 回放入口也直接读取 Parquet，需要实现基于 Arrow/Parquet 的事件读取适配，处理双时间戳、分侧顺序、分片边界与事件布局，并与当前 NPZ 回放逐项对照。这个改动应单独验收，再决定是否替换回放缓存格式。

## 四、用同一批记录比较压缩格式

本次取 2026-08-01 盘口 Parquet 开头的 1,000,000 条记录，保留相同的 13 个字段及类型，分别写入 CSV + ZSTD、Parquet + Snappy、Parquet + ZSTD。Parquet 行组设为 250,000 条，每种格式读回后与原表逐项比较一致。MB 按 1,000,000 字节计算。

| 格式 | 大小 | 写入时间 | 读回时间 |
| --- | ---: | ---: | ---: |
| CSV + ZSTD 3 | 7.87 MB | 0.275 秒 | 0.057 秒 |
| Parquet + Snappy | 5.88 MB | 0.151 秒 | 0.127 秒 |
| Parquet + ZSTD 3 | 4.44 MB | 0.154 秒 | 0.021 秒 |
| Parquet + ZSTD 9 | 4.34 MB | 0.209 秒 | 0.017 秒 |

这个样本中，Parquet + ZSTD 3 比 CSV + ZSTD 3 减少约 43.5% 存储，比 Parquet + Snappy 减少约 24.5%。级别 9 的额外空间收益和写入耗时见表，可按归档频次决定。

结果来自一段盘口记录。交易活跃度、字段类型、行组、排序方式和特征数都会改变压缩率。读写时间为本机单次测量，包含缓存与组件初始化影响；容量结论应在更多日期和研究表上复测。已有原始 CSV 与 HFT Parquet 的采集口径不同，直接比较它们的整日大小会混入源数据差异。 [格式测试结果](../../workspace/results/data_inspection/storage_benchmark/results.json)

## 五、字段和目录怎样设计

时间戳和成交、订单、更新编号使用 64 位整数，并在字段名或元数据中写清时间单位。可空编号使用可空整数类型。原始价格和数量保留来源精度，规范化后可使用十进制或明确步长的整数表示；归一化研究特征可以评估 Float32，以降低内存和存储。

盘口归档保留全量深度事件、快照标记和原始顺序。前五档或前十档视图作为派生研究表单独生成。快照批次、增量衔接和重连恢复的信息也随数据保存。

标准行情按类型和日期文件组织，快照保持来源行序，成交按交易所时间排序，研究读取时使用交易所时间加固定延迟。当前标准及研究Parquet使用ZSTD 3和100,000行组。特征组定义与来源内嵌文件元数据，标签按版本和周期单独保存。

| 数据层 | 建议做法 |
| --- | --- |
| 原始档案 | 保留网盘原件及来源记录；在有收益时生成规范化 Parquet |
| 云端热数据 | 只保留当前研究需要的日期，复用已经校验的分区 |
| 引擎缓存 | 按日期生成 NPZ，记录来源和转换参数，可在确认可重建后清理 |
| 特征与标签 | Parquet + ZSTD，按日期和版本分区，训练时读取需要的列 |
| 订单、成交和权益 | 保留验收用原始导出，批量研究时生成 Parquet 分析表 |

## 六、怎样估算经济性

存储成本与保存容量和持续时长有关。按容器云指南的共享存储示例，长期减少 100 GB，30 天约减少 34.56 元存储费。如果传输按出口流量收费，较小文件还会减少传输量。

实际总成本还包括转换、重复读取和重新生成。已有的原始 CSV.zst 可以继续作为可靠档案来源，标准行情及分组Parquet用于反复研究，NPZ缓存正在运行的事件回放日期。按这种方式安排，能够控制多种格式同时保留带来的容量增长。

下一步先围绕已验证的数据建立 CPU 特征与预测基线，用少量日期比较训练与执行的实际耗时；再根据瓶颈决定 GPU 和直接 Parquet 回放接口的投入。 [数据组织与处理流程](data_requirements.md)
