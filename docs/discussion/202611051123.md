### 为什么这样选？

你的项目文档有一组很有价值的实测结果。2026 年 7 月 12 日，你在 Apple M5、16 GB 内存上已经完成了一整天 BTCUSDT 的验证：

| 任务      | 实测耗时     | 峰值内存     |
| ------- | -------- | -------- |
| 原始数据转换  | 308.38 秒 | 2.78 GiB |
| M0 行情回放 | 208.94 秒 | 约 71 MiB |
| M1 交易策略 | 14.29 秒  | 约 71 MiB |

注意 M0 和 M1 的运行内容及计时范围不同，因此不能仅凭两者耗时判断哪个引擎更快。

但数据已经说明一个事实：现有 C++ 回测程序并不缺内存，甚至在本地 16 GB 机器上都能够运行整日行情。

因此你现在租服务器，真正需要改善的是三个方面。

首先是单核性能。高频事件驱动回测需要按照时间顺序更新订单簿、处理事件和维护策略状态。对于一个交易日，现有引擎主要沿单线程执行，因此单核性能比单纯增加核心数更重要。

其次是多任务吞吐。你未来可能需要在 30 个日期上验证多个预测周期和参数组合。不同日期的回放可以放到独立进程并行运行，因此 8—16 个较强的逻辑 CPU 对研究效率有帮助。

最后是训练数据的内存和存储。你当前回放只需要几十 MiB，但后面生成数千万行特征、进行滚动训练时，64 GB 内存就会比较有意义。

我建议优先比较 CPU 的实测性能，而非只按 vCPU 数量购买。可以在候选服务器上用同一个数据日运行 `benchmark_replay`，比较单日耗时、峰值内存和并发多个日期后的总吞吐。

如果 8 核实例的单任务性能明显优于 16 核共享实例，前者也可能更适合初期研究。

### 服务器费用怎样控制？

你文档中的容器云报价示例是 2.98 元/小时，另有按容量和时间计算的存储费用。这个报价对应一个带 GPU 的套餐，因此不能直接当作推荐 CPU 主机的市场价格。

我建议采用按需计算资源加持久化存储的方式：平时在本地写 C++ 和做小数据实验，云服务器只在数据转换、批量回测和模型训练时运行，数据存储单独保留。

30 天数据的原始压缩文件和当前 NPZ 缓存，按照你已经测得的单日规模，通常只需要几十 GB；真正可能迅速增加空间占用的是高频特征矩阵、重复实验输出和多份转换缓存。

因此 500 GB NVMe 是合理的起点，暂时不需要直接购买 TB 级数据盘。若后续要在服务器上长期保留大量全事件级特征，再按实测容量扩展。

## 二、既然是超高频研究，为什么不直接使用 GPU？

这个问题需要区分两种计算任务：

高频事件处理强调单次决策延迟，机器学习训练强调大量样本的计算吞吐。

它们对硬件的需求不同。

CPU

事件驱动计算

读入一笔行情 → 更新盘口 → 更新特征 → 计算信号 → 生成决策。

依赖上一事件状态，控制分支较多，要求单次处理及时。

GPU

大规模并行计算

读取数千万训练样本 → 批量矩阵计算 → 更新模型参数。

大量独立或可并行的计算，追求总体吞吐和训练速度。

举个例子。

假设 C++ 策略接收到一笔新的买卖盘口更新，只需要更新几个滚动特征，再执行一个线性模型。这个任务的计算量非常小，而且下一次计算依赖更新后的盘口和策略状态。

把每笔事件都送到 GPU，再等待 GPU 返回预测结果，很可能会引入数据传输、任务启动和同步开销。

而且，事件数量很大并不意味着它们都可以同时计算。订单簿更新存在严格的时间顺序，交易决策还会改变后续订单和库存状态。

NVIDIA 官方 CUDA 最佳实践也明确区分了适合 CPU 的顺序计算和适合 GPU 的大规模并行计算，并强调数据传输成本。

[image](https://www.google.com/s2/favicons?domain=https://docs.nvidia.com\&sz=32)

docs.nvidia.com



但是，你后面如果训练 LightGBM、MLP、Transformer，情况就完全不同。

| 工作内容                 | 建议资源          | 原因               |
| -------------------- | ------------- | ---------------- |
| L2 盘口重建与事件回放         | CPU           | 事件具有顺序依赖         |
| OBI、OFI、滚动成交特征在线更新   | CPU           | 单次计算量较小，强调增量处理   |
| Ridge、Lasso 等简单模型    | CPU 优先        | 先建立稳定、便于解释的统计基线  |
| 大规模 LightGBM         | CPU/GPU 实测选择  | GPU 可以加速部分大样本训练  |
| MLP、Transformer、序列模型 | GPU           | 大量矩阵运算适合并行       |
| C++ 策略回测与订单模拟        | CPU           | 延迟、成交与持仓状态需要顺序推进 |
| 大规模离线特征矩阵计算          | CPU/GPU 按瓶颈选择 | 部分批处理可以有效并行      |

LightGBM 官方明确支持 GPU 训练，并展示了在较大、较密集数据集上的加速效果；XGBoost 也支持 CUDA 加速训练与预测。

[image](https://www.google.com/s2/favicons?domain=https://lightgbm.readthedocs.io\&sz=32)

LightGBM 4.7.0 documentation+1



所以我认为，你完全应该在项目中保留 GPU 训练能力，但没有必要从第一天开始持续租用 GPU。

### 未来推荐的 CPU + GPU 工作方式

CPU 研究主机

行情处理、特征生成、标签构造

特征与标签数据集

Parquet 分区，按日期与特征版本管理

按需 GPU 训练

LightGBM / MLP / Transformer，生成模型参数

C++ 回测与策略决策

加载模型，增量计算信号，生成交易动作

例如，先在 CPU 主机上处理 30 天行情，构造 100ms 间隔的特征和标签，然后启动一台 GPU 实例训练 MLP。训练完成后保存模型参数，将推理逻辑放回 C++ 策略程序。

开始可以考虑单张 16—24 GB 显存的 NVIDIA GPU，是否足够取决于样本数、特征维度、训练批次和模型规模。需要更大显存或多卡时，再根据实验结果升级。

我不建议为了可能使用 Transformer，就现在租一台长期运行的 GPU 服务器。 你当前 M2 的主要不确定性仍然是预测信号有没有价值，模型训练速度还不是已经证实的研究瓶颈。

## 三、这种研究流程是否符合成熟量化团队的做法？

整体方向是合理的。HftBacktest 的官方设计本身就是围绕高频行情回放、订单延迟、排队位置和成交模拟展开的。其文档还特别强调，回测必须充分理解与真实交易的差异，避免执行假设导致虚假的收益优势。

[image](https://www.google.com/s2/favicons?domain=https://hftbacktest.readthedocs.io\&sz=32)

hftbacktest



但没有一套所有高频量化机构通用的权威技术架构。不同团队对 C++、Python、GPU、研究数据平台和实盘系统的分工存在差异。

对于你这种以超高频 Alpha 研究为核心的项目，我更推荐下面的完整研究流程：

1\. 原始数据与质量控制

保留完整行情、检查时间戳、盘口更新连续性与数据来源

2\. C++ 增量特征计算

逐事件更新盘口和特征，按研究频率采样

3\. 研究数据集

保存特征、预测标签、样本时间与数据版本

4\. 离线模型研究与训练

统计检验、信号诊断、滚动样本外验证，必要时使用 GPU

5\. C++ 策略回测

加载模型或预测规则，完成交易决策和历史订单模拟

6\. 收益归因与实验迭代

分析净收益、成交质量、交易成本和市场状态

你现在已经有第一层和第五层的基础，M2 要重点建立第二、三、四层。

这里有一个特别重要的设计原则：

C++ 特征引擎应该直接处理完整事件流，但模型训练数据不需要保留每一条盘口事件对应的完整特征向量。

举个例子，你目前单日 BTCUSDT 大约有 9000 万条逻辑事件。

如果每条事件保存 20 个 `float32` 特征，一天仅特征矩阵就大约需要 7.2 GB，30 天约 216 GB。

但如果 C++ 每次收到事件都更新特征状态，只在每 100ms 生成一条训练样本，那么一天最多有 864000 个固定时间网格点。

同样保存 20 个 `float32` 特征，单日矩阵只有约 69 MB，30 天约 2.1 GB，尚未计入时间戳、标签和其他元数据。

以上为理论大小估算，未计入压缩，且假设全天连续、每 100ms 产生一个有效样本。

这意味着你可以保留完整的高频信息处理过程，同时把离线研究数据控制在合理范围。

当然，固定时间采样与按价格变化、成交等事件采样的统计性质不同。M2 可以先使用固定 100ms 网格，之后专门比较事件时间下的预测能力。

还有一个你项目文档中已经发现的问题必须优先处理：2026 年 8 月的两套行情源存在约 122ms 的本地时间差异。对于 100ms 预测，这个差异足以破坏标签与特征的时间对应关系。

因此，不同数据来源要先分别验证时间口径，不能直接拼接成同一个训练集。

新增模块的职责应该非常清楚：

我会特别强调一个设计：`feature_engine` 要独立于 `market_maker`。

它只负责根据市场事件更新信息，不需要知道策略当前持仓，也不需要知道订单是否成交。

这样相同的特征计算逻辑可以用于离线研究和 C++ 策略回测，减少研究与策略实现之间的计算差异。

### 当前架构还有两个需要特别注意的地方

第一，`MarketObserver` 目前每 100ms 提取一次前十档。

这适合 M0 检查盘口，但 M2 的 OFI、盘口增量和短期成交特征不能只依赖这些定期快照。

因为两个采样时刻之间可能已经发生大量挂单、撤单和成交。

所以 M2 的 `feature_engine` 必须逐事件接收盘口和成交变化，更新内部特征状态；`sampling` 再决定什么时候输出研究样本。

这样既保留完整的事件信息，又避免产生过大的训练数据集。

第二，M1 对第三方引擎的撤单拒绝回报做过兼容处理。

你目前把这部分逻辑放在 `detail/trading_engine.hpp`，并有相应测试。这个边界暂时可以保留。

但未来如果升级 `hftbacktest-cpp`，必须先运行订单与账本的回归测试，尤其是部分成交、撤单竞态和重复回报的情况。

这类引擎兼容逻辑应始终与 Alpha、策略和训练代码隔离。

目前对架构的判断基于上传的设计和实现文档；完整源码没有包含在这份压缩包中，因此具体类之间是否还有不合理的依赖，需要在代码审查时再确认。

## 五、现在使用 NPZ 合理吗？要不要切换 Parquet？

结论很明确：NPZ 继续用于 C++ 回测，Parquet 开始用于研究数据。现在不建议将回测引擎的 NPZ 接口直接替换成 Parquet。

原因是这两种格式擅长的任务不同。

NPZ 是 NumPy 数组文件的打包格式，适合存放已经确定结构的事件数组。你现在的 `hftbacktest-cpp` 已经有经过验证的 NPZ 读取接口。

Parquet 是面向分析的列式存储格式，把相同字段的数据集中存储，适合只读取部分特征列、按日期过滤和进行大规模统计研究。Apache Arrow 官方也明确支持按列读取、按条件过滤和分区数据集。

hftbacktest+1



### 我建议的数据分层

| 数据层      | 建议格式                | 原因                        |
| -------- | ------------------- | ------------------------- |
| 原始行情档案   | 原始 CSV.zst / CSV.gz | 保留来源数据，方便重新验证和转换          |
| C++ 回放事件 | NPZ                 | 现有引擎直接读取，已经完成整日验证         |
| 高频研究特征   | Parquet + ZSTD      | 便于只读取指定特征、日期和时间段          |
| 预测标签     | Parquet + ZSTD      | 便于与特征按时间对齐、构建训练集          |
| 模型预测结果   | Parquet             | 便于不同模型和预测周期比较             |
| 订单、成交与权益 | CSV 或 Parquet       | 小规模保留 CSV，大批量分析使用 Parquet |

你现有文档其实已经提出了类似方案，我认为方向正确。

而且已经有一个实际实验：对相同的 100 万条盘口记录，Parquet + ZSTD 3 为 4.44 MB，CSV + ZSTD 3 为 7.87 MB。

但这里有一个需要明确的地方：这个实验比较的是原始记录的两种存储方式，还没有证明 Parquet 比当前 C++ 引擎使用的 NPZ 更快。

NPZ 与 Parquet 的真正比较，应该使用相同的事件内容，统计文件大小、读取与解压耗时、事件转换耗时、峰值内存和完整回放耗时。

而当前 `hftbacktest-cpp` 的 NPZ 读取器还具有特定的压缩和归档格式限制。直接换成 Parquet 意味着需要另行开发事件读取适配，并验证双时钟调度和事件顺序。
